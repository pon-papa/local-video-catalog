# Python runtime の配布方式（比較と推奨）

- 作成日: 2026-08-15
- 目的: 一般利用者が **Python を意識せずに** 使える One-Folder 配布にする
- 前提: 巨大な installer は作らない。One-Folder 原則を崩さない

現状（v1 実装時点）は「外部 Python を要求し、無ければ案内する」方式である。
`Start.cmd` が `py -3` → `python` の順に探し、3.13 未満なら日本語で
インストール方法を示して止まる。

---

## 比較

| 方式 | 配布サイズ | 利用者の手間 | One-Folder | 保守性 | 実行の透明性 |
|---|---|---|---|---|---|
| A. 外部 Python を要求（現状） | 約 190 KB | **Python を自分で入れる** | 保たれる | 最良 | 高い（.py のまま） |
| B. embeddable package を同梱 | 約 15〜20 MB | **なし** | 保たれる | 良い | 高い（.py のまま） |
| C. PyInstaller で exe 化 | 約 30〜50 MB | なし | 保たれる | やや悪い | 低い（中身が見えない） |
| D. installer（MSI 等） | — | インストール操作 | **崩れる** | 悪い | 低い |

### A. 外部 Python を要求（現状）

- **利点**: 配布物が極端に小さい。更新が速い。コードがそのまま読める
- **欠点**: **一般利用者にとってこれが最大の障壁。** 「Python とは何か」から
  始まる。Microsoft Store 版と python.org 版で挙動が違う場面もある
- 開発クローンではこの方式のままでよい

### B. embeddable package を同梱（**推奨**）

python.org が配布する Windows embeddable package（zip・約 11 MB、
展開後 約 15〜20 MB）を `runtime\` へ置き、`Start.cmd` が
**同梱 runtime を最優先で使う**。見つからなければ従来どおり外部 Python を探す。

```
local-video-catalog\
├─ runtime\python.exe        ← 同梱（利用者は存在を意識しない）
├─ src\local_video_catalog\
└─ Start.cmd                 ← runtime\python.exe を最優先で使う
```

- **利点**
  - 利用者の手間がゼロ。展開して `Start.cmd` を押すだけ
  - **One-Folder 原則をそのまま満たす**（runtime も APP_ROOT の中）
  - フォルダーごとコピー・移動しても runtime がついてくる
  - コードは `.py` のまま。**中身を確認できる**（配布の透明性）
  - このアプリはサードパーティ依存がゼロなので、embeddable の
    「pip も site-packages も無い」制約が問題にならない
- **欠点**
  - 配布サイズが約 100 倍になる（それでも 20 MB 程度）
  - tkinter は embeddable package に**含まれない**ため、
    `tcl/` と `_tkinter.pyd` を別途同梱する必要がある（**要検証**）
  - python.org の再配布条件（PSF ライセンス）に従い、
    ライセンス表記を同梱する必要がある

### C. PyInstaller で exe 化

- **利点**: 単一 exe。利用者から見て最も「普通のアプリ」らしい
- **欠点**
  - **子プロセスの起動方式を作り直す必要がある。** 現在は
    `sys.executable -m local_video_catalog.pipeline` で自分自身を
    再実行しているが、凍結後はこれが使えない
  - 誤検知されたウイルス対策ソフトにブロックされることがある
  - **中身が見えない。** 「外部へ送信しない」ことを利用者が
    確認できなくなる。このアプリの性格上これは軽くない欠点
  - ビルド環境の維持が必要（開発機以外でも再現できるように）

### D. installer

**採用しない。** One-Folder 原則に反する。インストール先・
アンインストーラー・レジストリという、この設計が避けてきたものが
すべて戻ってくる。

---

## 推奨

**B（embeddable package の同梱）を推奨する。**

理由:

1. 利用者の手間が消える一方で、**One-Folder 原則を一切崩さない**
2. コードが `.py` のまま残るので、「外部へ送信していない」ことを
   利用者自身が確かめられる。ローカル解析を売りにする以上、
   ここは C より明確に優れている
3. 現在の「自分自身を `-m` で再実行する」構造をそのまま使える
4. サードパーティ依存ゼロなので embeddable の制約に当たらない

### 進め方

段階的に入れる。**A を残したまま B を足す**のが安全。

| 段階 | 内容 |
|---|---|
| 1 | `Start.cmd` に「`runtime\python.exe` があれば最優先」の分岐を足す（無ければ現状どおり） |
| 2 | tkinter を含む最小 runtime の作り方を検証する（`tcl/` と `_tkinter.pyd` の同梱可否） |
| 3 | `tools\make_release.py` に `--with-runtime` を足し、runtime 入りの zip も作れるようにする |
| 4 | PSF ライセンス表記を `LICENSE` へ追記 |

段階 2 が成立しない場合（tkinter を embeddable へ載せられない場合）は、
**C を再検討する**。その場合も `.py` を読める形で同梱することを条件にしたい。

**この検討で実装全体を止めない。** 現状の A でも配布物は動作する
（配布フォルダーを展開して合成動画で一周できることを確認済み）。
